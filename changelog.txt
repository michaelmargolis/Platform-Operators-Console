POC v160 | Heave bar polarity and Debug-tab paint isolation
------------------------------------------------------------------
The QPainter transform display now reverses the sign of Heave (third DOF)
when passing values to the widget. Other five DOFs are unchanged. The raw
sample remains unchanged for telemetry, controls, CSV capture, diagnostics,
and the transform viewer.

A source-level UPDATE_TRANSFORM_BARS_ON_DEBUG_TAB switch in ui/main_window.py
controls whether transform bar values are fed to QPainter while the Debug tab
is selected. Default False skips bar updates on Debug for profiling processing
utilisation and jitter. True enables updates on Debug at the existing 20 Hz
sample rate. Outside Debug, the widget behaves normally. No extra timer.

POC v159 | 20 Hz QPainter transform-level display
------------------------------------------------------------------
Replaces the six independent QProgressBar controls in grp_transform_levels
with one compact TransformBarsWidget drawn using QPainter. The single widget
shows Surge, Sway, Heave, Roll, Pitch and Yaw. Values from -100 to +100
fill left/right from a centre zero line; both directions use green.
Percentages at the right are enabled by SHOW_TRANSFORM_BAR_VALUES in
ui/main_window.py; they can be disabled without altering the UI files.
If horizontal space is extremely limited the percentage captions hide
automatically to preserve useful bar width.

Input follows sampleUpdated at the unchanged 20 Hz rate. No timer or
throttling is introduced. The painter requests a repaint only when displayed
integer values change and the widget is visible. Both standard and compact
800x480 .ui layouts use the same scalable widget; the compact layout now
shows the transform group, previously hidden.

Files changed:
- ui/ui_widgets.py v6 -> v7: add TransformBarsWidget.
- ui/main_window.py v68 -> v69: install widget; replace progress updates.
- ui/poc_main.ui v13 -> v14: replace progress-bar grid with placeholder.

# README_v158.txt  ver 1
POC v158 — 20 Hz processing utilization and frame jitter diagnostics.

Changes since v157:
- core/poc_core.py ver 49 -> 50:
  * Instrument each 50 ms _data_tick callback using time.perf_counter().
  * Publish last callback processing utilization (% of 50 ms budget),
    start-to-start scheduling jitter (% deviation from 50 ms), and the
    rolling maximum processing utilization over 200 frames (~10 seconds).
  * Timing runs in a finally block, including exceptions and early returns.
  * Existing processing callback content remains unchanged.
  * The new diagnostics are platform-neutral: Windows and Raspberry Pi.
- ui/main_window.py ver 67 -> 68:
  * Add one compact "Frame timing" line to the Debug tab.
- tests/test_poc_performance_v158.py ver 1: regression tests for
  timing, start-to-start jitter, rolling maximum, and exceptions.
- file_versions.txt ver 152 -> 153: register and update tracked versions.
- README_v158.txt ver 1: this note.

Expected Debug output (illustrative):
    Frame timing   : processing=24%  max(10s)=39%  jitter=4%

Meaning:
- processing=24%: the latest _data_tick callback ran for 12 ms.
- max(10s)=39%: the longest of the last 200 callbacks ran for ~19.5 ms.
- jitter=4%: interval between the latest two callback starts differs from
  50 ms by 2 ms. It does not mean 4% CPU use.
- A processing percentage above 100% is an overrun of the 50 ms budget.

These metrics cover only the main data callback. The separate simulator
service timer, other Qt callbacks, and GUI rendering are not included in
processing %, but may appear indirectly as data-timer jitter.

Install: unzip v158 over v157, preserving paths. No changes to platform
control, physical inputs, Festo, simulator adapters, or .ui Designer files.
Run tests on a developer machine with PyQt5 and all dependencies installed.

# README_v157.txt  ver 1
POC v157 - NoLimits2 Normalized Height heave (Phase 2 initial test settings)

Delta over POC v156. No changes to physical platform kinematics, workplace
limits, pressure output, networking, NL2 protocol, or simulator state machine.

NL2 Input Control now offers three session-only heave sources:
  Legacy Height (startup default; same code/calibration as v156)
  Vertical G (same G-based cue + temporary classical Z washout as v156)
  Normalized Height (fixed per-ride height bounds and per-ride amplitude)

Normalized Height maps track minimum to +A and track maximum to -A, clipped
outside the calibrated bounds. In this inverted platform a greater NL2
height therefore contracts/raises the platform. Amplitude A is applied to
the simulator's normalized heave before the normal POC gains and intensity.
The seven initial calibrated profiles are in sims/nolimits2/config.py:
  Mdx Logo Coaster       3.2 .. 32.7 m     A=0.80
  Blackbird              5.9 .. 41.0 m     A=0.90
  Fenrir                 2.7 .. 45.6 m     A=0.70
  Forest Mountain Park   4.6 .. 48.1 m     A=0.90
  GrandNational          2.5 .. 21.2 m     A=0.90
  Hybris                -3.9 .. 87.8 m     A=0.90
  Wilderness Park      -20.5 .. 72.1 m     A=0.90
Bounds were rounded outwards from completed 2026-10-21 capture extrema.
No calibrated bounds are supplied for Flying Beast, Scenic Run or Tilt Coaster.
The UI disables Normalized Height for those rides; the adapter rejects it.
When switching from a calibrated to uncalibrated ride while Normalized Height
is selected, the simulator explicitly reverts to Legacy Height and POC reports
that change. All selection remains disabled while physically activated.

Changes:
  sims/nolimits2/config.py ver 13 -> 14
  sims/nolimits2/sim.py ver 31 -> 32
  core/poc_core.py ver 48 -> 49
  ui/main_window.py ver 66 -> 67
  README.md ver 10 -> 11
  tests/test_nl2_normalized_height_v157.py ver 1 (new)
  README_v157.txt ver 1 (new)
  file_versions.txt ver 151 -> 152

Validation: NL2 adapter/recording tests and heave-limit regression tests;
Python compilation and version-check manifest. Live POC hardware remains to
be tested before using the normalized mode with riders. The 70-90% settings
are geometry-screening values, not validated actuator dynamics or safety
limits. The existing floor and muscle workspace constraints remain active.

POC v156 | Historical source: README_v156.txt
------------------------------------------------------------------
# README_v156.txt  ver 1
POC v156 - NL2 request-ID collision and ride-study startup diagnostics

Delta over v155. Root cause: NL2Protocol generated request IDs from elapsed
milliseconds. The normal Sim.service() startup sends LOAD_PARK immediately
followed by telemetry/station requests, often within the same millisecond.
These different requests then share the same ID. When telemetry reports
"Not in play mode" while the park loads, that ERROR could be mistaken for a
LOAD_PARK failure, despite the requested park load succeeding. Similar
collisions could affect other asynchronous NL2 operations in normal POC.

The protocol now uses a lock-protected incrementing 32-bit request ID counter.
This changes neither the NL2 packet format nor simulator state machine: the
adapter still loads the configured default at connection, and a selected park
is loaded through Sim.select_experience(). IDs remain distinct when multiple
commands are sent in one service cycle. Genuine NL2 LOAD_PARK errors continue
to be reported and handled by the recorder.

The recorder passes the first requested study ride as an optional startup
index to Sim. This avoids loading Logo Coaster before a Blackbird-only study.
The normal POC caller omits that argument and still loads the configured
default. Subsequent study rides continue through Sim.select_experience() on
the same persistent connection, with the existing bounded busy retry.

Changed: sims/nolimits2/nl2_protocol.py, sims/nolimits2/sim.py,
         tools/capture_nl2_rides.py, tests/test_nolimits2_adapter.py,
         tests/test_capture_nl2_rides_v153.py,
         tests/test_nl2_request_ids_v156.py (new), file_versions.txt,
         README_v156.txt (new).

Validation: NL2 request collision reproduced by regression test against v155,
then fixed. Offline tests/version check run; live NL2 verification required.

Run: python tools/capture_nl2_rides.py --rides Blackbird --repeats 1

POC v155 | Historical source: README_v155.txt

# README_v155.txt  ver 1
POC v155 - NL2 ride-study persistent session and busy-load retry

Delta over v154. Changes limited to the standalone ride-study recorder, its
unit tests, version manifest and these release notes.

The recorder now connects to the NoLimits2 adapter once, verifies the normal
startup default LOAD_PARK response, and keeps that connection across every
selected ride and repeat. It uses the existing Sim.select_experience() path
for each distinct ride; repeat runs on the same coaster use the normal
return-to-station, prepare_for_activation(), and dispatch sequence.

If NL2 rejects a requested park with 'Application is processing another
operation', the recorder continues to service NL2, waits two seconds and
reissues that same load through the existing adapter _begin_ride_load() path.
This is necessary because the adapter has already set _selected to the
requested target, so select_experience(target) would otherwise be a no-op.
The retry is limited to five retries. Other errors and response timeouts
remain fatal and no recording will be mislabelled as the requested ride.

The NL2 adapter, default ride configuration, normal POC control, and SHS
are unchanged. The recorder does not communicate with platform hardware.

Run: python tools/capture_nl2_rides.py --rides 1,2 --repeats 3

Live NL2 operation (particularly the park busy/retry transition) still
requires confirmation on the user's simulator PC.

#README_v153.txt  ver 1
POC v153 - NL2 repeatable ride telemetry study (additive utility)

Changed files:
- tools/capture_nl2_rides.py (new, ver 1): standalone NL2 API ride-selection,
  repeated-run and raw/normalized 20 Hz capture to CSV. No POC, Festo or GPIO
  control is started.
- tests/test_capture_nl2_rides_v153.py (new, ver 1): offline selection/schema tests.
- file_versions.txt (ver 147 -> 148): register both new files.
- README_v153.txt (new, ver 1): usage and limitations.

Run from the POC repository:
    python tools/capture_nl2_rides.py --list
    python tools/capture_nl2_rides.py --rides 1,3 --repeats 3
    python tools/capture_nl2_rides.py --rides all --repeats 2 --host 192.168.0.4

Without --rides/--repeats, the tool prompts interactively. NL2 must be
running with its telemetry API enabled, and configured park files must exist
on the NL2 simulator PC. Use the tool INSTEAD OF the normal POC client while
recording; they should not both command the same NL2 session.

Each run starts with park loading/manual station preparation, then POC's
normal NL2 dispatch logic. CSV output goes to captures/nl2_ride_study/.
Each fresh NL2 frame is logged once; approximate sampling request is 20 Hz,
not a guarantee NL2 itself produces exactly 20 unique frames per second.
Columns include raw pose, position (pos_y is vertical height in metres),
G-force, quaternion, all six simulator-normalized DOFs, and two alternative
heave calculations. The actual physical platform is not commanded.

Runs are recorded through arrival back at the dispatch-ready station. If a
ride does not support the standard station dispatch sequence or times out,
check its CSV (may be partial) and log; some parks may require custom handling.
This version has only been tested offline with the adapter's unit tests;
NL2 park loading and repeat dispatch require validation with the simulator.

POC v150 - Twin applied real transform, parking state, Output-tab switch
=====================================================================
Apply this delta to the COMPLETE POC v149 installation.

POC_TWIN protocol version 1 adds TWO optional fields:
  parking_state: "PARKED" | "UNPARKED" | "PARKING" | "UNPARKING"
  applied_transform_real: [X,Y,Z,roll,pitch,yaw] or null
Translations are mm; rotations radians; pose is the backend's last transform
actually used to calculate the actuator lengths after workspace limiting.
Existing normalized 'transform' is unchanged. Snapshots continue to contain
commanded pressures and lengths. The additional fields are part of the same
snapshot, not an independently observed physical state.

Platform Output tab, full-size and compact layouts:
  Twin checkbox enables/disables UDP output for this RUN only.
  Initially checked when the configured digital_twin destination is enabled.
  Caption shows the address:port from poc_config.json; '-' means unconfigured
  and disables the checkbox. This UI NEVER edits poc_config.json.

Use the configured 'digital_twin': {'address': 'a.b.c.d', 'port': 10020}
for output. '-' remains disabled. If the checkbox is off, transmissions stop;
checking it again opens a new UDP sender at the same configured destination.

Only output/protocol/UI files were changed. No POC motion or parking controller
state machine changes. Run python version_check.py after extracting.
